1. Arquitetura do Cluster Kubernetes

O Kubernetes opera sob o paradigma declarativo: você define o estado desejado e o orquestrador age continuamente para manter o estado real alinhado.

Control Plane (O Cérebro)
  • kube-apiserver: Ponto central de comunicação REST de todo o cluster.
  • etcd: Banco chave-valor consistente e de alta disponibilidade (estado do cluster).
  • kube-scheduler: Decide em qual nó de trabalho (Worker) cada Pod será alocado.
  • kube-controller-manager: Loops de controle de réplicas, nós e endpoints.
Worker Nodes (A Força de Trabalho)
  • kubelet: Agente local que garante que os contêineres descritos no PodSpec estejam rodando e saudáveis.
  • kube-proxy: Gerencia regras de rede iptables/IPVS para viabilizar Services.
  • Container Runtime: Motor de baixo nível compatível com CRI (ex: containerd, CRI-O).

2. Pods, ReplicaSets e Deployments

O Pod é a menor unidade de execução no Kubernetes. Jamais crie Pods soltos em produção: use sempre um Deployment.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: pedidos-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: pedidos
  template:
    metadata:
      labels: { app: pedidos }
    spec:
      containers:
      - name: api
        image: registry.empresa.com/pedidos:v2.1
        ports:
        - containerPort: 8080
Por que usar Deployment?
  • Auto-recuperação (Self-healing): Se um nó cair, o controller recria os Pods perdidos em outro nó disponível.
  • Rolling Updates: Atualiza versões gradualmente sem indisponibilidade.
  • Rollback Imediato: Permite reverter releases com kubectl rollout undo caso erros ocorram.

3. Service Discovery e Balanceamento Interno

Pods nascem e morrem com novos IPs dinâmicos o tempo todo. O Service provê um IP fixo virtual e DNS para abstrair os Pods.

Tipo de ServiceComo FuncionaCaso de Uso
ClusterIP (Padrão)Expõe um IP interno acessível exclusivamente de dentro do cluster k8s.Comunicação interna entre microsserviços (ex: API acessando banco).
NodePortAbre uma porta estática de alto nível (30000-32767) em cada nó do cluster.Acesso direto simplificado em laboratórios ou redes privadas.
LoadBalancerProvisiona um Balanceador de Carga real na nuvem pública (AWS ALB, GCP LB).Exposição de serviços críticos diretamente para tráfego externo.
Ingress / Gateway APIRoteador de camada 7 (HTTP/HTTPS) baseado em rotas, subdomínios e TLS.Porta de entrada unificada para múltiplos serviços com certificado SSL.

4. Gerenciamento de Recursos e Autoscaling (HPA)

Definir limites de computação é mandatório para viabilizar o escalonamento horizontal e evitar quedas do cluster.

Requests vs. Limits
  • Requests: Quantidade de CPU/RAM reservada e garantida para o Pod ser agendado em um nó.
  • Limits: Teto máximo permitido. Se o contêiner estourar o limite de CPU, sofrerá throttling (lentidão). Se estourar a RAM, sofrerá OOMKilled (reinício forçado).
# HorizontalPodAutoscaler (HPA)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: pedidos-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: pedidos-api
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

5. Probes: Liveness, Readiness e Startup

O Kubernetes precisa de sondas explícitas para saber quando um nó pode receber tráfego e quando deve ser reiniciado.

Liveness Probe

Detecta deadlocks e falhas fatais.

Se falhar, o Kubernetes reinicia o contêiner imediatamente.

Readiness Probe

Verifica se a app está pronta para atender requisições.

Se falhar, o Pod é removido do Service (não recebe tráfego), mas não é reiniciado.

Startup Probe

Para aplicações legadas com inicialização lenta.

Bloqueia as outras probes até que a carga inicial termine sem matá-la precocemente.

6. Gerenciamento com Helm Charts

O Helm atua como o gerenciador de pacotes do Kubernetes, permitindo parametrizar manifestos YAML por ambiente (Dev, Staging, Prod).

Estrutura de um Helm Chart
  • Chart.yaml: Metadados, nome e versão do pacote.
  • values.yaml: Variáveis padrões (versão de imagem, réplicas, limites de memória).
  • templates/: Manifestos k8s dinâmicos que utilizam Go Templates para injetar os valores definidos.
Comandos Essenciais no Ciclo de Vida
  • helm install meu-app ./chart: Realiza o deploy do release.
  • helm upgrade meu-app ./chart -f values-prod.yaml: Aplica novas configurações.
  • helm rollback meu-app 1: Desfaz um deploy defeituoso instantaneamente para a versão anterior.

Exercício 1: Diagnóstico de Falha de Probes

Cenário: Uma API remota em Kubernetes começa a sofrer lentidão momentânea devido a uma consulta pesada em banco. O endpoint de verificação demora mais que o timeout configurado, e o k8s imediatamente reinicia o Pod, derrubando os usuários ativos em cascata.

Exercício 2: Pré-requisitos para o HPA

Cenário: Um engenheiro configura um Horizontal Pod Autoscaler (HPA) para escalar réplicas quando o uso de CPU atingir 75%. No entanto, o comando `kubectl get hpa` exibe `/75%` e o cluster nunca escala automaticamente durante picos.

Exercício 3: Exposição de Banco de Dados

Cenário: Uma equipe remota provisionou um cluster PostgreSQL dentro do Kubernetes. O banco só deve ser acessado pelos microsserviços internos do cluster e jamais deve receber tráfego direto ou portas abertas para a internet pública.

Exercício 4: O Mecanismo do OOMKilled

Cenário: Ao verificar o status dos pods com `kubectl get pods`, você nota a mensagem `CrashLoopBackOff` e o evento detalhado exibe `Exit Code 137 - OOMKilled`.

Módulo Concluído

Boas Práticas de Orquestração

O Kubernetes consolida a infraestrutura distribuída em torno de padrões declarativos e auto-recuperáveis.

Resiliência Operacional

Nunca utilize Pods nus. Use Deployments com réplicas distribuídas em diferentes zonas de disponibilidade (Multi-AZ) e defina probes conservadoras.

Governança Declarativa

Padronize deploys utilizando Helm Charts com versionamento semântico, facilitando testes e reversões imediatas via esteira automatizada.
