Aula 09 — Infraestrutura como Código (IaC)

Automatização de infraestruturas em nuvem para equipes distribuídas: Terraform, OpenTofu, gerenciamento de estado remoto, conciliação e prevenção a Drift.

Linguagem HCL

Sintaxe declarativa, Providers, Resources, Data Sources e variáveis reutilizáveis.

Estado Remoto & Locks

Armazenamento em S3/GCS com controle de concorrência distribuído (DynamoDB/State Lock).

Detecção de Drift

Identificação e correção automática de alterações manuais feitas fora do código versionado.

1. O Fim do Gerenciamento Manual (ClickOps)

Configurar servidores clicando em consoles de nuvem é inviável em operações remotas escaláveis e auditáveis.

Perigos do "ClickOps"
  • Ausência de rastreabilidade e histórico de auditoria sobre quem alterou o que.
  • Divergência entre ambientes (Snowflake Servers): Produção diferente de Staging.
  • Tempo de restauração de desastres (RTO) medido em dias, reconstruído manualmente.
Vantagens da IaC Declarativa
  • Idempotência: Rodar o mesmo código 10 vezes produz sempre o mesmo estado.
  • Versionamento no Git: Code Reviews e Pull Requests para mudanças de infraestrutura.
  • Automação Completa: Criação e destruição de ambientes efêmeros sob demanda.

2. Sintaxe Básica em HCL (HashiCorp Configuration Language)

O código descreve o recurso que você deseja; os Providers traduzem isso em chamadas de API da nuvem.

# Provisionamento de bucket com bloqueio de acesso público
resource "aws_s3_bucket" "dados_remotos" {
  bucket = "empresa-dsr-producao-dados"

  tags = {
    Environment = "prod"
    ManagedBy = "terraform"
  }
}

resource "aws_s3_bucket_public_access_block" "seguranca" {
  bucket = aws_s3_bucket.dados_remotos.id
  block_public_acls = true
  block_public_policy = true
  restrict_public_buckets = true
}
Grafo de Dependências
  • O Terraform monta um Directed Acyclic Graph (DAG) automaticamente.
  • Ele sabe que o recurso aws_s3_bucket_public_access_block depende do aws_s3_bucket existir primeiro, paralelizando tudo que for independente.

3. Ciclo de Execução: Init, Plan, Apply e Destroy

O fluxo de trabalho padrão para garantir previsibilidade antes de qualquer alteração no ambiente de nuvem.

ComandoO que realiza internamente?Impacto na Nuvem
terraform initBaixa os plugins dos providers e inicializa os backends de estado remoto.Nenhum (apenas configuração local).
terraform planCompara o código local com o arquivo de estado e a nuvem real, gerando um diff executável.Somente leitura (seguro de executar).
terraform applyExecuta as chamadas de API necessárias (criação, alteração ou destruição de recursos).Altera a infraestrutura real.
terraform destroyDestrói todos os recursos controlados pelo estado deste workspace.Exclusão destrutiva da infra.

4. Gerenciamento do `terraform.tfstate`

O arquivo de estado mapeia o código com os recursos reais. Em equipes remotas, ele jamais pode ser commitado no Git.

O Risco do Estado Local
  • Vazamento de Segredos: O tfstate contém senhas e tokens em texto puro gerados por recursos de banco de dados.
  • Race Conditions: Se dois desenvolvedores remotos rodarem apply ao mesmo tempo, o estado corrompe a infraestrutura.
Remote Backend com State Locking
  • Armazenamento seguro em bucket S3/GCS privado criptografado com KMS.
  • State Locking: Uso de banco de locks (ex: DynamoDB) para travar o arquivo de estado enquanto um apply estiver em execução.

5. Módulos e Isolamento de Ambientes

Evite arquivos monolíticos gigantes. Utilize módulos reutilizáveis e separe Prod de Dev.

Módulos Terraform

Agrupam recursos relacionados em um componente reutilizável.

  • Entradas parametrizadas via variables.tf.
  • Recursos padronizados em main.tf.
  • Valores expostos para outros módulos via outputs.tf.
Isolamento de Diretórios

Mantenha diretórios separados com seus próprios arquivos de estado:

infra/
├── modules/ (vpc, rds, eks)
└── environments/
    ├── dev/ (main.tf, backend.tf)
    └── prod/ (main.tf, backend.tf)

6. Drift Detection: A Realidade da Nuvem

Drift ocorre quando alguém altera manualmente um recurso via console ou CLI sem passar pelo código.

1. O Incidente

Durante um plantão, um analista altera o Security Group manualmente para liberar a porta 22 para um IP externo.

2. A Detecção

Na manhã seguinte, a pipeline de CI/CD executa terraform plan e aponta a discrepância entre o código e a nuvem.

3. A Reconciliação

O terraform apply automático revoga a liberação manual, restaurando a conformidade segura da infraestrutura.

Exercício 1: Concorrência em Times Remotos

Cenário: Dois engenheiros remotos executam terraform apply em suas estações no mesmo minuto contra a mesma infraestrutura de produção. Sem State Locking configurado, o arquivo `.tfstate` é corrompido.

Exercício 2: O Conceito de Idempotência

Cenário: Você executa terraform apply e ele cria 5 servidores virtuais. Sem alterar nenhuma linha de código, você executa o comando terraform apply novamente cinco minutos depois. O que o Terraform fará?

Exercício 3: Exposição de Dados no Statefile

Cenário: Ao provisionar um banco de dados AWS RDS via Terraform, você gerou uma senha aleatória com o recurso `random_password`. Onde essa senha foi gravada e qual o risco envolvido?

Exercício 4: Resposta a Modificação Manual

Cenário: Um administrador alterou manualmente o tipo de uma máquina virtual de `t3.micro` para `t3.large` diretamente no painel da AWS. O código do Terraform continua configurado como `t3.micro`. O que acontecerá no próximo `terraform apply`?

Módulo Concluído

Pilares de IaC em Soluções Remotas

A infraestrutura como código transforma a nuvem em software auditável e reprodutível.

Trabalho Colaborativo

Centralize o estado em storage remoto isolado com State Locking habilitado e utilize pipelines automatizadas para validar o plan antes de cada merge.

Imutabilidade e Segurança

Bloqueie acessos manuais via console em contas de produção. Toda e qualquer alteração de rede, DNS ou máquinas deve nascer de um commit auditado.
