1. Anatomia do Contêiner: O Que Há sob o Capô?

Contêineres não são máquinas virtuais completas com hipervisor: são processos nativos do Linux isolados por recursos do próprio kernel.

Linux Namespaces (Visibilidade)
  • PID: O processo dentro do contêiner acredita ser o PID 1.
  • NET: Cada contêiner recebe sua própria interface de rede, tabela de rotas e portas isoladas.
  • MNT: Pontos de montagem do sistema de arquivos restritos à imagem.
  • IPC / UTS / USER: Isolamento de sockets de memória, hostname e mapeamento de UID/GID.
Control Groups - cgroups (Limites)
  • CPU Shares & Quotas: Impede que um processo remoto sature todos os núcleos da máquina servidora.
  • Memory Limits: Define o limite estrito de RAM; se ultrapassado, o kernel aciona o OOM Killer (Out Of Memory).
  • I/O Blkio: Controla velocidade de leitura e escrita em disco para evitar gargalos de I/O.

2. Dockerfiles Otimizados: Multi-Stage Builds

Em produção remota, imagens pesadas consomem banda de rede desnecessária e expõem compiladores que auxiliam invasores.

# Estágio 1: Build da aplicação
FROM golang:1.22-alpine AS builder
WORKDIR /app
COPY go.* ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -o server .

# Estágio 2: Imagem final mínima em produção
FROM gcr.io/distroless/static-debian12:nonroot
WORKDIR /
COPY --from=builder /app/server /server
USER nonroot:nonroot
ENTRYPOINT ["/server"]
Benefícios Técnicos
  • Redução drástica de tamanho: Redução de ~800MB (imagem SDK) para ~20MB (apenas binário compilado).
  • Segurança: Sem bash, curl ou gerenciadores de pacotes (`apt/apk`) que possam ser usados em caso de exploração RCE.
  • Usuário Não-Root: Bloqueia quebras de isolamento (container escape) contra o root do host.

3. Drivers de Rede no Docker

A escolha do driver de rede define como contêineres comunicam-se entre si e com a internet externa.

4. Padronização de Ambientes Remotos: Docker Compose

Garante que todo o time de engenharia trabalhe com topologias de rede, bancos e variáveis idênticas em qualquer estação remota.

services:
  api:
    build: .
    environment:
      - DB_HOST=db
    networks:
      - backend
    depends_on:
      - db

  db:
    image: postgres:16-alpine
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - backend

networks:
  backend: # Isolada do mundo externo
volumes:
  pgdata:
Resolução de Nomes Interna
  • Em redes Docker customizadas, o Docker DNS embutido (`127.0.0.11`) resolve o nome do serviço (ex: `db`) automaticamente para o IP interno do contêiner.
  • Nenhuma porta do PostgreSQL precisa ser exposta no host (`ports:` omitido), mantendo o banco isolado dentro da bridge backend.

5. Persistência de Dados: Volumes vs. Bind Mounts

Contêineres são efêmeros por natureza. A destruição de um contêiner destrói todo o seu sistema de arquivos de gravação (UnionFS).

Volumes Gerenciados (`docker volume`)
  • Armazenados em uma área exclusiva gerenciada pelo Docker (`/var/lib/docker/volumes/`).
  • Isolados do acesso direto do sistema operacional hospedeiro.
  • Alta performance de I/O em macOS e Windows com WSL2.
  • Padrão mandatório para bancos de dados de produção.
Bind Mounts (`/caminho/host:/app`)
  • Espelha uma pasta física da máquina host para dentro do contêiner.
  • Permite que alterações no código local reflitam instantaneamente via hot-reload.
  • Depende da estrutura de arquivos e permissões UID do SO host.
  • Ideal apenas para desenvolvimento e depuração local remota.

6. Hardening e Proteção do Host em Nuvem

Práticas essenciais para impedir que um contêiner comprometido em nuvem assuma o controle do servidor físico.

Jamais use `--privileged`

Essa flag desabilita todos os mecanismos de segurança de cgroups e namespaces, dando acesso a todos os dispositivos de hardware do host.

Drop de Linux Capabilities

Remova privilégios desnecessários do kernel adicionando --cap-drop=ALL e habilitando apenas o mínimo exigido (ex: NET_BIND_SERVICE).

Read-Only Root Filesystem

Configure --read-only na imagem base, impedindo que invasores baixem mineradores ou scripts executáveis em caso de invasão.

7. Healthchecks Nativos do Docker Engine

O Docker precisa saber se o processo não está apenas de pé (PID ativo), mas se consegue responder a requisições com sucesso.

# Adicionando healthcheck sintético no Dockerfile
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD wget -q --spider http://localhost:8080/healthz || exit 1
Status de Ciclo de Vida

Estados monitoráveis:

  • starting: Janela de inicialização (grace period).
  • healthy: O comando retornou código 0 sucessivamente.
  • unhealthy: Excedeu o número de retries e pode acionar reinicialização automática com restart policies (`restart: unless-stopped`).

Cenário: Um desenvolvedor remoto percebe que um processo rodando dentro de um contêiner trava o servidor inteiro por consumir 100% da memória RAM física da máquina hospedeira.

Exercício 2: Resolução de Nomes e Isolamento

Cenário: Você inicia dois contêineres na rede bridge padrão (default bridge) sem flags de rede. Ao tentar fazer um ping pelo nome do outro contêiner (`ping api`), o comando falha dizendo que o host não existe.

Exercício 3: Segurança e Multi-Stage Build

Cenário: Um time remoto está fazendo deploy de imagens Docker em instâncias AWS EC2 que possuem 1.5GB de tamanho. O pipeline de CI/CD está demorado e o scanner de segurança alertou dezenas de vulnerabilidades críticas do pacote de compilação.

Exercício 4: Prevenção de Perda de Dados

Cenário: Um contêiner com MySQL de testes foi atualizado em produção via comando `docker stop mysql && docker rm mysql` seguido por um `docker run` da nova versão. Todo o banco de dados sumiu.
